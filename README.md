# 在线五子棋 (Gomoku Online)

一个基于 **uni-app**（微信小程序） + **Cloudflare Workers + Durable Objects** 的在线五子棋对弈平台。

## 技术架构

```
┌─────────────────────┐     WebSocket      ┌──────────────────────────────────┐     WebSocket      ┌─────────────────────┐
│   玩家 A (小程序)     │◄──────────────────►│  Cloudflare Worker              │◄──────────────────►│   玩家 B (小程序)    │
│                     │     信令中转       │  ├─ GomokuMatchRoom (DO) ──────│                    │                     │
│  本地棋局逻辑 ✅     │                    │  │  匹配队列 / 房间 / 转发      │                    │  本地棋局逻辑 ✅     │
│  禁手判断 ✅         │                    │  │  所有 WS 在同一 DO 实例 ✅   │                    │  禁手判断 ✅         │
│  胜负判断 ✅         │                    │  └──────────────────────────────│                    │  胜负判断 ✅         │
└─────────────────────┘                    └──────────────────────────────────┘                    └─────────────────────┘
```

### 为什么这样分配？

| 模块 | 放在哪里 | 原因 |
|------|----------|------|
| **棋局逻辑**（落子、禁手、胜负） | **客户端本地** | Worker 免费版 CPU 时间有限，棋局运算放在本地既快又省钱 |
| **匹配/配对** | **Worker (DO)** | 需要全局共享状态，Durable Objects 保证所有 WS 在同一实例 |
| **消息转发** | **Worker (DO)** | 透传，不解析内容，几乎零成本 |
| **棋盘渲染** | **客户端** | 天然就该在 UI 层 |

### 为什么用 Durable Objects 而不是 KV？

- **WebSocket 对象不能跨 Worker 实例共享**。KV 存的是序列化数据，但 WebSocket 是内存中的对象。
- **Durable Objects** 确保同一个房间的所有 WebSocket 连接都路由到**同一个 DO 实例**，WebSocket 对象直接在内存中共享。
- 免费版 DO 每天 100 万次请求，足够使用。

## 功能特性

### 游戏规则
- ✅ 15×15 标准棋盘
- ✅ 黑白双方轮流落子（黑棋先手）
- ✅ 四方向五子连珠判定（横、竖、正斜、反斜）
- ✅ **三三禁手**（黑方禁止同时形成两个活三）
- ✅ **四四禁手**（黑方禁止同时形成两个四）
- ✅ **长连禁手**（黑方禁止六子及以上连珠）
- ✅ 平局（棋盘满无位置可下）
- ✅ 每步 30 秒限时

### 联机功能
- ✅ **随机匹配**：进入队列，系统自动配对
- ✅ **创建房间**：生成 6 位短房间号（排除易混淆字符 O/0/I/1），发给好友加入
- ✅ **加入房间**：输入 6 位房间号加入好友对局
- ✅ **不能加入自己的房间**
- ✅ **空房间自动过期**（30 分钟无人加入）
- ✅ **离开/销毁房间**：游戏结束后离开 → 房间销毁；房主离开 → 房间销毁
- ✅ 心跳保活（每 10 秒 ping）
- ✅ 断线检测与通知

### 交互特性
- ✅ **锁定-确认落子机制**：点击棋盘先锁定位置（显示阴影），确认后再正式落子，防止误触
- ✅ **预落子（跨回合继承）**：任意回合都可锁定位置，对方也能看到你的预落子标记。轮到你的回合时如果该位置没被占，预落子自动继承
- ✅ **双方预落子可见**：自己的预落子（脉冲动画）和对手的预落子（半透明虚线）同时显示在棋盘上
- ✅ **对方回合灰化**：轮到对手时棋盘半透明灰化遮罩，清晰区分回合
- ✅ **双方倒计时显示**：标明当前是谁的时间（"你的时间" / "对手的时间"）
- ✅ **超时自动提交**：如果锁定了位置但超时未确认，自动提交该位置，不算超时判负
- ✅ **禁手预警**：锁定位置时提示该位置是否可能触发禁手
- ✅ **认输确认**：点击认输弹出确认对话框
- ✅ **获胜连线高亮**：五子连珠时高亮显示获胜棋子
- ✅ **胜负颜色区分**：赢家绿色背景，输家红色背景
- ✅ **最后一步标记**：最后落子的棋子用红圈标记
- ✅ **再来一局（双方确认）**：游戏结束后双方点击"再来一局"，都确认后自动开始新对局（不退出房间），也可返回大厅

## 本地开发

### 前置条件

1. [HBuilderX](https://www.dcloud.io/hbuilderx.html) — uni-app 开发 IDE
2. 微信开发者工具（小程序预览/调试）
3. Node.js (用于 wrangler CLI 部署 Worker)
4. Cloudflare 账号（免费即可）

### 部署 Worker

```bash
# 安装 wrangler
npm install -g wrangler

# 登录 Cloudflare
wrangler login

# 进入 server 目录
cd server

# 首次部署（wrangler.toml 已配置好 DO 绑定和 migration）
wrangler deploy
```

### 配置 WebSocket 地址

部署后修改 `utils/websocket.js` 中的地址：

```javascript
const WS_URL = 'wss://gomoku.legotrain.eu.org/ws'
```

### 运行小程序

1. 用 HBuilderX 打开项目目录
2. 菜单栏: **运行 → 运行到小程序模拟器 → 微信开发者工具**

2. 在 `manifest.json` 的 `mp-weixin.appid` 中填入 AppID
3. **开发阶段**：微信开发者工具 → 详情 → 本地设置 → 勾选"不校验合法域名"
4. **真机预览**：需要在公众平台配置 WebSocket 域名白名单
   - 开发管理 → 开发设置 → 服务器域名 → socket 合法域名

5. **真机调试**（推荐开发阶段使用）：工具 → 真机调试 → 真机调试 1.0（USB 通道，不走域名白名单）

## 核心逻辑详解

### game-logic.js — 禁手判断

禁手是五子棋最复杂的规则，**仅对黑方生效**：

```
禁手检测流程（落子前）：
1. 模拟落子
2. 长连检测 → 六子及以上连续 → 长连禁手
3. 四四检测 → 两个或以上的"四" → 四四禁手
4. 三三检测 → 两个或以上的"活三" → 三三禁手
5. 撤销模拟
```

- **"四"的定义**：存在恰好一个空位可以补成五子连珠
- **"活三"的定义**：三子连线且两端开放，在任一端落子后能形成活四

### 锁定-确认落子机制

```
玩家触摸棋盘 → 锁定位置（显示阴影）
    ↓
检查禁手 → 显示禁手预警
    ↓
点击"确认落子" → 正式落子 → 发送 WebSocket
    ↓
30 秒未确认但有锁定 → 自动提交（不算超时）
    ↓
30 秒未锁定位置 → 超时判负
```

这种设计的好处：
- 防止误触导致立即落子
- 给玩家确认机会
- 超时时优先使用锁定位置（保护玩家不因误操作判负）

### 预落子对齐问题（关键设计点）

预落子（Pre-lock）允许玩家在任何时刻（包括对方回合）锁定一个位置，跨回合继承。这带来了一个对齐问题：

```
回合线：
  我的回合          对手的回合         我的回合
    │                  │                 │
    ├── 预落子 (3,3) ──┤── 对手落子 ─────┤── 预落子 (3,3) 还在
    │  禁手检查 ✅     │  改变棋盘状态    │  但禁手状态可能变了 ❓
    │                  │  没占 (3,3) ✅   │  没有重新检查禁手
```

**核心问题**：预落子时的禁手检查基于**当时的棋盘状态**。对手落子后棋盘变了，但预落子位置保留了下来，禁手状态可能已经失效：

| 场景 | 问题 |
|------|------|
| 对手落子改变了预落子位置的禁手状态 | 预落子时不是禁手，对手落子后变成了禁手，但玩家不知道 |
| 对手回合预落子（不做禁手检查） | 对手回合的预落子直接跳过禁手检查，轮到己方时带着未经验证的预落子进入自动提交倒计时 |
| 超时自动提交 | 如果预落子是在旧棋盘状态下设置的，超时自动提交可能提交一个禁手位置 |

**当前处理方式**：
- 对手落子占了预落子位置 → 清空（简单直接）
- 对手没占 → 保留预落子，但**不重新检查禁手**
- 超时自动提交时 → 直接提交锁定位置，**不重新检查禁手**

**为什么不重新检查？** 禁手检查在落子确认时由服务端最终裁决，客户端的禁手提示仅作为参考。预落子继承的设计优先保证操作流畅性（玩家不需要每回合重新锁定），禁手正确性由服务端兜底。

### 棋盘 DOM 对齐 — 子像素偏移

**现象**：棋盘网格线、触摸覆盖层、棋子三者在某些屏幕尺寸下出现 1-2px 的错位，点击位置和实际落子位置不一致。

**根因**：`cellSize` 由屏幕宽度除以 14（15×15 棋盘有 14 个间隔）计算得出，在很多屏幕尺寸下是小数（如 `375 / 14 ≈ 26.7857`）。旧代码用 `left: padding + col * cellSize - offset` 手动计算像素坐标，`Math.round` 的取整误差在跨列累积后，导致 DOM 覆盖层和棋盘网格线之间出现可见偏移。

**修复方案**：棋子定位改用 `left: 50%; top: 50%; transform: translate(-50%, -50%)`，让浏览器自己处理子像素居中。触摸覆盖层改用 Grid 布局，每个交叉点对应一个 Grid 单元格，彻底消除手动坐标计算。

**为什么难 debug**：偏移量只有 1-2px，在大部分屏幕上看不出来。只有在特定屏幕宽度（`cellSize` 小数部分接近 0.5 时）才会触发，且微信开发者工具模拟器和真机表现不一致。

### 服务端架构演进

项目经历了三个阶段：

1. **纯内存（初版）**：`rooms` 和 `connections` 都存在 Worker 全局变量中。问题：免费版 Worker 多实例不共享内存，匹配和房间在不同实例间不可见。

2. **KV（第二版）**：房间数据存 Cloudflare KV，WebSocket 连接存内存。问题：WebSocket 对象不能序列化，对手的 WS 在另一个实例上就发不了消息。

3. **Durable Objects（最终版）**：所有 WebSocket 路由到同一个 DO 实例。DO 自带持久化存储 + 内存共享，完美解决。**推荐方案。**

## 常见问题

**Q: 匹配不到人？**
A: 需要两个玩家同时在匹配队列中。可以试试创建房间，把 6 位房间号发给朋友。

**Q: Worker 部署后真机连接不上？**
A: 检查 WebSocket 地址是否正确。真机预览需要在微信公众平台配置 socket 合法域名。推荐先用"真机调试"（USB 通道）。

**Q: 棋盘显示不全？**
A: 棋盘组件会根据屏幕宽度自动计算格子大小。如果仍有问题，检查 `board-renderer.js` 中的 `cellSize` 计算。

**Q: 房间号输入框只能输入 6 位？**
A: 故意的。房间号由 6 位大写字母+数字组成（排除易混淆的 O/0/I/1），输入框限制 maxlength=6。
